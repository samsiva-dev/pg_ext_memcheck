## ext_memcheck.flush_violations()

Moves all entries from the in-memory shared ring buffer (`ViolationLog`) into the persistent `ext_memcheck.violation_log` table and returns the count of rows inserted i.e., **the number of violations flushed**. It also clears the ring buffer, making it ready to log new violations.

```sql
-- flushes all pending violations to the table ext_memcheck.violation_log
-- and returns the count of violations
SELECT ext_memcheck.flush_violations();

-- query the violation log table directly
-- includes all historical violations, not just the flushed ones
SELECT * FROM ext_memcheck.violation_log;
```

**Returns:** `int` — number of violations flushed to the table.

**Notes:**
- The ring buffer is bounded by `MEMCHECK_MAX_VIOLATIONS` set to constant `256` (not configurable). When full, oldest entries are overwritten. Call `flush_violations()` regularly to avoid data loss.
- Returns zero if no violations have been detected since the last flush.

### Violation log table schema

| Column | Type | Description |
|---|---|---|
| `id` | `int` | Auto-incrementing violation ID |
| `ts` | `timestamptz` | Timestamp of the violation |
| `backend_pid` | `int` | PID of the backend that detected the violation |
| `check_type` | `text` | Type of the check that detected the violation like context_leak, wrong_context, etc. |
| `severity` | `text` | Severity of the violation like CRITICAL, WARNING, INFO etc. |
| `detail` | `text` | Human-readable description of the violation |
| `source_lib` | `text` | The library that triggered the violation (e.g., buggy_pg_ext) |

### Severity levels
| Level | Memory Leak Size |
|---|---|
| `ERROR` | ≥ 1 MB |
| `WARNING` | ≥ 64 KB and < 1 MB |
| `INFO` | >= min_leak_bytes and < 64 KB |

## ext_memcheck.begin()

Opens a manual test window and sets the `pg_ext_memcheck.memcheck_mode` mode based to the provided target. 

```sql
SELECT ext_memcheck.begin('executor');  -- check executor phase only
SELECT ext_memcheck.begin('all');       -- check planner + executor phases
```

**Parameter:** `target_mode TEXT` — one of `'all'`, `'executor'`, or `'none'`. Unrecognised values default to `'all'`.

**Returns:** `text` — confirmation message.

Use this when you want finer-grained control than the automatic executor-hook window:

```sql
SELECT ext_memcheck.begin('executor');

-- Run some queries or operations here,
-- that you want to test for leaks or other violations.

SELECT * FROM ext_memcheck.end();
```

## ext_memcheck.end()

Closes the current manual test window by setting `pg_ext_memcheck.memcheck_mode` to `'none'` and returns any violations detected during the window directly as a result set. 

But do not flush the ring buffer into the `violation_log` table — violations remain there until you call `ext_memcheck.flush_violations()`. This allows you to inspect the violations in more detail or join them with other tables before flushing.

```sql
SELECT * FROM ext_memcheck.end();
```

**Returns:** `TABLE(check_type TEXT, severity TEXT, detail TEXT, ts TIMESTAMPTZ, source_lib TEXT)` — all violations detected during the test window.

Call `SELECT ext_memcheck.flush_violations()` afterwards to also persist any ring-buffer entries to the `violation_log` table.

## ext_memcheck.run_scenario()

Runs a named **stress scenario**. Violations are written to the shared ring buffer; call `ext_memcheck.flush_violations()` to read them by flushing the buffer.

```sql
SELECT ext_memcheck.run_scenario(scenario_name := 'growth_benchmark', iterations := 200, workload := 'SELECT 1');
SELECT ext_memcheck.run_scenario(scenario_name := 'tx_abort_loop', iterations := 50, workload := 'SELECT 1');
```

**Parameters:**

| Parameter | Type | Default | Description |
|---|---|---|---|
| `scenario_name` | `text` | — | Scenario name. Currently available: `growth_benchmark`, `tx_abort_loop`. See [Stress Scenarios](/scenarios/). |
| `iterations` | `int` | `100` | Number of iterations to execute within the scenario. |
| `workload` | `text` | `'SELECT 1'` | SQL query to execute within each iteration of the scenario. User can provide a **`custom query`** to simulate different workloads. |

**Returns:** `text` — confirmation message.

<Aside type="note" title="Partial implementation">
  `growth_benchmark` and `tx_abort_loop` are available now. Additional scenarios (`context_reset_storm`, `concurrent_backends`, `shmem_sentinel_probe`, `dsm_lifecycle_check`, `wrong_context_probe`) are planned for Phase 2. Passing an unknown scenario name raises an error.
</Aside>

## ext_memcheck.clear_violations()
Utility function to clear all entries from the `ext_memcheck.violation_log` table. Does not affect the in-memory ring buffer.

```sql
SELECT ext_memcheck.clear_violations();
```

## GUC parameters

Set these in `postgresql.conf` or with `SET` at session scope (`PGC_USERSET` — no restart required).

| Parameter | Type | Default | Description |
|---|---|---|---|
| `pg_ext_memcheck.memcheck_mode` | `enum` | `all` | Controls which parts of query execution are instrumented. See below. |
| `pg_ext_memcheck.min_leak_bytes` | `int` | `8192` | Minimum context growth in bytes required to log a violation. Smaller growth is silently ignored. |

## pg_ext_memcheck.memcheck_mode

The primary control knob for the extension. Determines which execution phases are hooked and checked.

```sql
-- Disable all instrumentation (zero overhead)
SET pg_ext_memcheck.memcheck_mode = 'none';

-- Check only executor-phase allocations (default for focused testing)
SET pg_ext_memcheck.memcheck_mode = 'executor';

-- Check all phases: planner + executor
SET pg_ext_memcheck.memcheck_mode = 'all';
```

| Value | Hooks active | When to use |
|---|---|---|
| `none` | None | Disable the extension without unloading it; zero runtime overhead. |
| `executor` | `ExecutorStart`, `ExecutorEnd` | Focused testing of Executor phase allocations. |
| `all` | Planner `planner_hook` + Executor `ExecutorEnd` | Full sweep — catches leaks that happen during planning and execution. |

**Recommended workflow:**

1. Start with `executor` to isolate your function under test.
2. Promote to `all` before marking the extension as clean — planner hooks and utility handlers are common sources of leaks that `executor`-only misses.
3. Set to `none` in shared CI environments where another test suite is running, to avoid cross-contamination of violation logs.

## Violation types reference

| Type | Phase | Description |
|---|---|---|
| `context_leak` | 1 | A `MemoryContext` created during query execution was not freed by `ExecutorEnd`. |
| `wrong_context` | 1 | A `palloc()` landed in a long-lived context (`TopMemoryContext`, `CacheMemoryContext`, or a user-configured forbidden context). |
| `shmem_overrun` | 2 | Sentinel bytes after a `ShmemAlloc()` allocation were overwritten. |
| `dsm_leak` | 2 | A DSM segment was attached during a test window but not detached before the window closed. |
| `use_after_reset` | 2 | Extension function crashed or produced incorrect results after a forced `MemoryContextReset()`. |
| `context_bloat` | 2 | Total allocated bytes in the context tree increased monotonically across all iterations of a growth benchmark scenario. |
