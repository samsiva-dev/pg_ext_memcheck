  pg_ext_memcheck is **not production-safe**. Use it only in development and CI environments.

## Prerequisites

- PostgreSQL 14 or later (server headers required)
- `pg_config` in your `PATH`
- A C compiler (`gcc` or `clang`)

## Installation

<Steps>

1. **Clone the repository**

   ```bash
   git clone https://github.com/samsiva-dev/pg_ext_memcheck.git
   cd pg_ext_memcheck
   ```

2. **Build and install**

   ```bash
   make
   sudo make install
   ```

   This uses PGXS to build against your installed PostgreSQL headers and places the extension files in the correct `$libdir`.

3. **Configure `postgresql.conf`**

   Add the extension to the preloaded libraries so the background worker and hooks are registered at startup:

   ```ini
   # postgresql.conf
   shared_preload_libraries = 'pg_ext_memcheck'
   ```

   Restart PostgreSQL after making this change.

4. **Create the extension**

   ```sql
   CREATE EXTENSION pg_ext_memcheck;
   ```

</Steps>

## Your first check

Test a simple function from any extension you are developing:

```sql
-- Start a check window in executor mode
SELECT ext_memcheck.begin('executor');

-- Call the function you want to inspect
SELECT your_extension.some_function('input');

-- End the window; returns violations detected during this window
SELECT * FROM ext_memcheck.end();

-- Also flush any remaining ring-buffer entries to the log table
SELECT ext_memcheck.flush_violations();

-- Query the violation log for details
SELECT * FROM ext_memcheck.violation_log ORDER BY ts DESC;
```

If `flush_violations()` returns zero rows, no leaks or wrong-context allocations were detected for that invocation.

A violation row looks like this:

| Column | Example |
|---|---|
| `ts` | `2026-05-10 14:32:01 UTC` |
| `backend_pid` | `12345` |
| `detail` | `"Context present in post-query snapshot but not pre-query"` |
| `severity` | `warning`, `info`, `critical`, etc. |
| `check_type` | `context_leak`, `wrong_context_allocation`, `shmem_overrun`, etc. |

## Run a built-in stress scenario

```sql
-- Run the growth benchmark scenario (measures context growth over repeated calls)
SELECT ext_memcheck.run_scenario('growth_benchmark', 100);

SELECT ext_memcheck.flush_violations();
```

```sql
-- Run the tx_abort_loop scenario (tests memory cleanup on transaction abort)
SELECT ext_memcheck.run_scenario('tx_abort_loop', 50);

SELECT ext_memcheck.flush_violations();
```

<Aside type="note" title="Available scenarios">
  `growth_benchmark` and `tx_abort_loop` are available now. Additional scenarios (`context_reset_storm`, `concurrent_backends`, etc.) are planned for Phase 2. See the [Stress Scenarios](/scenarios/) page for details.
</Aside>

## GUC parameters

| Parameter | Type | Default | Description |
|---|---|---|---|
| `pg_ext_memcheck.memcheck_mode` | `enum` | `all` | `all` / `executor` / `none` — controls which execution phases are hooked. See [API reference](/api/#pg_ext_memcheckmemcheck_mode). |
| `pg_ext_memcheck.min_leak_bytes` | `int` | `8192` | Context growth smaller than this (in bytes) is silently ignored. |

For focused testing of a single function, set mode to `executor` to reduce noise:

```sql
SET pg_ext_memcheck.memcheck_mode = 'executor';
```

## Regression testing
The `pg_ext_memcheck` extension includes a test suite that can be run using `pg_regress` (comes with PostgreSQL source). To run the tests:

From the extension directory, run:
```bash
PG_CONFIG=pg_config ./test/run_tests.sh
```
